# 018. Kafka 장애 시 WebSocket 수신 스레드 블로킹

- 날짜: 2026-11-15 발견, 2026-11-25 해결
- 관련: #41, #42, ADR 0020, 성능 001

## 증상
시세 발행 실패 콜백의 MDC 전파(#41)를 확인하려고 Kafka를 멈췄더니, 예상한 비동기 콜백 실패 대신 이런 로그가 나왔다.

```
[binance] 메시지 처리 실패 - ...
KafkaException: Send failed
  at KafkaTemplate.send(...)
  at KafkaTickerPublisher.publish(...)
  at BinanceWebSocketClient.onMessage(...)
  at ExchangeWebSocketClient$Listener.onText(...)
Caused by: TimeoutException: Topic market.ticker.v1 not present in metadata after 60000 ms.
```

메시지 속 체결 시각은 06:31:14, 실패 로그는 06:32:14로 정확히 60초 차이였다.

## 원인
- Kafka가 사라지자 프로듀서가 토픽 메타데이터를 잃었다.
- 비동기 `send()`도 메타데이터가 없으면 `max.block.ms`(기본 60초) 동안 **호출한 스레드를 블로킹**한다.
- 호출한 스레드가 WebSocket 수신 스레드였으므로 수신이 멈췄다. 코드 주석 "비동기 전송: WebSocket 수신 스레드를 막지 않음"과 실제 동작이 달랐다.
- 메시지가 60초마다 하나씩만 처리되어 좀비 감지(60초간 수신 없음)가 아슬아슬하게 오작동하지 않았다. `dispatch()`가 메시지를 받자마자 `lastMessageAt`을 갱신한 뒤 블로킹되었기 때문이다.

## 영향 (Before 측정)
Kafka 약 3분 40초 중단 시 (Binance BTC·ETH, 성능 001):
- 수신 완전 정지 (60초에 1건씩만 처리)
- 프로듀서 버퍼에 있던 42건이 약 2분(`delivery.timeout.ms`) 뒤 일괄 실패
- 받았지만 발행 실패 44건
- 수신하지 못한 체결 약 19,000건 추정 (정상 평균 초당 110건 × 약 220초 기준)
- 복구 직후 운영체제 네트워크 버퍼에 쌓여 있던 4,661건이 한꺼번에 처리됨

MSA 선택 이유인 "장애 격리"가 깨진 상태였다. Kafka 장애가 거래소 수집까지 멈췄다.

## 해결
수신과 발행을 분리했다 (ADR 0020).
- WebSocket 스레드는 보관함(큐)에 넣기만 하고 즉시 반환
- 전담 발행 스레드 1개가 순서대로 전송, 실패하면 같은 체결 재시도
- 보관함이 넘치면 버린 건수와 유실 구간 기록
- `max.block.ms` 5초, `delivery.timeout.ms` 5분

## 결과 (After 측정)
같은 방법으로 Kafka 약 3분 중단:
- 수신 정지 없음 (10초당 +592 ~ +4,224)
- 보관함에 최대 30,125건 적재, 복구 후 10초 안에 비워짐
- 받았지만 발행 실패 0건, 넘침 0건, 미수신 0건

## 배운 점
- "비동기 API"도 내부적으로 블로킹하는 구간이 있을 수 있다. 문서와 실제 동작을 장애 실험으로 확인한다.
- 외부 의존성 호출을 수신 경로에서 분리해야 장애가 전파되지 않는다.
- 같은 Kafka 발행이라도 데이터 성격(시세 vs 환율)에 따라 장애 대응이 다르다.
- 원래 목적(#41 검증)과 다른 실험 결과도 그냥 넘기지 않고 이슈로 남겼기 때문에 발견할 수 있었다.
