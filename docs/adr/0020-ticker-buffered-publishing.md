# 0020. 시세 수신·발행 분리: 보관함과 전담 발행 스레드

- 상태: 채택
- 날짜: 2026-11-25
- 관련: #42, #41, 트러블슈팅 018, 성능 001

## 맥락
- WebSocket 수신 스레드가 `KafkaTemplate.send()`를 직접 호출했다.
- Kafka 장애 시 `send()`가 메타데이터 대기(`max.block.ms`, 기본 60초)로 수신 스레드를 블로킹해 수신이 정지하고 대량의 체결을 잃었다 (트러블슈팅 018).
- 3단계 실시간 캔들(고가·저가·거래량)과 4단계 정합성 대사에는 체결이 빠짐없이 필요하다.
- 코인이 늘면 초당 체결 수가 늘어난다.

## 선택지
- A: `max.block.ms`만 줄이기
- B: 보관함(큐)을 두고 수신과 발행을 분리
- C: B + `max.block.ms` 축소

## 결정
C. 수신 스레드는 보관함에 넣기만 하고, 전담 발행 스레드 1개가 순서대로 Kafka로 보낸다.

## 원칙
1. **받는 스레드는 절대 막지 않는다**: `queue.offer()`(꽉 차면 기다리지 않음)만 호출하고 즉시 반환한다.
2. **짧은 장애는 하나도 잃지 않는다**: 전담 스레드는 전송에 실패하면 같은 체결을 다시 보낸다. 성공해야 다음 체결로 넘어가므로 순서도 유지된다.
3. **넘치면 기록해 두고 나중에 채운다**: 보관함이 넘치면 버린 건수(`dropped`)와 거래소·코인별 체결 시각 기준 유실 구간을 기록한다. 체결 원본은 거래소에 있으므로 공백 보정에서 REST로 채운다.
4. **환율은 대상이 아니다**: 하루 한 번 고시되어 하나하나가 중요하므로 동기 발행 + 스케줄러 재시도를 유지한다.

## 이유
- A만으로는 메시지마다 수 초씩 막히는 것이 여전하다.
- 처음에는 "최신 시세만 필요하니 넘치면 버린다"를 검토했으나, 캔들·대사에 모든 체결이 필요해 "버리지 않고, 넘친 구간은 기록해 보정한다"로 바꿨다.
- 전담 스레드를 1개로 두어 순서를 보장한다. 평소 Kafka 프로듀서는 묶음 전송(`linger.ms`)으로 처리량이 충분하다.

## 구성
- `BufferedTickerPublisher`(`@Primary`)가 `KafkaTickerPublisher`를 감싼다 (데코레이터).
- 보관함: `ArrayBlockingQueue`, 용량 `collector.ticker-buffer.capacity` = 50,000
- 재시도 간격: `collector.ticker-buffer.retry-backoff` = 1초
- 전담 스레드: 플랫폼 스레드 `ticker-publisher`, `SmartLifecycle`로 시작·종료. Kafka 프로듀서 내부의 `synchronized` 대기에서 가상 스레드 고정(pinning)을 피하려고 플랫폼 스레드를 쓴다.
- Kafka 프로듀서: `max.block.ms` 5초(전담 스레드가 오래 멈추지 않게), `delivery.timeout.ms` 5분(프로듀서 버퍼 안의 체결이 2분 만에 버려지지 않게)
- MDC: 전담 스레드에서 `exchange`만 다시 붙인다 (체결마다 MDC 전체를 복사하면 메모리가 크게 늘어남)
- 메트릭: `collector.ticker.received`, `collector.ticker.published{result}`, `collector.ticker.dropped`, `collector.ticker.buffer.size`(gauge)

## 숫자 근거
- 정상 시 Binance(BTC, ETH) 평균 초당 약 110건, 최대 약 220건 (성능 001 Before)
- Upbit(BTC, ETH)는 초당 약 3건 수준
- 두 거래소 합쳐 초당 약 300건 × 3분 ≈ 54,000건 → 50,000건으로 시작
- 급등락 시 초당 약 900건 관측 (성능 001 After) → 이때 버팀 시간은 약 1분

## 결과
Kafka 약 3분 중단 실험에서 수신 정지가 사라지고 유실 0건을 확인했다 (성능 001).

## 트레이드오프
- `published{result=failure}`의 의미가 "유실 건수"에서 "전송 시도 실패 횟수"로 바뀌었다. 실제 유실은 `dropped`로 본다.
- 앱 종료 시 보관함에 남은 체결은 버려진다 (건수만 로그) → 6단계 graceful shutdown에서 처리한다.
- 유실 구간은 로그로만 남긴다 → 공백 보정을 만들 때 저장 방식(DB, 토픽)을 정한다.
- 보관함은 메모리라 앱이 죽으면 함께 사라진다.
- 다시 볼 조건: 코인 확장으로 초당 수신량이 늘거나 `dropped`가 관측될 때 보관함 크기 재조정, collector 다중 인스턴스로 코인 분할(수평 확장 묶음).
