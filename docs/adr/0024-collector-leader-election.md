# 0024. collector 다중 인스턴스: 리더 선출(active-standby)

- 상태: 채택
- 날짜: 2026-11-26
- 관련: #65, ADR 0008, ADR 0020, ADR 0021, 성능 002

## 맥락
- collector가 한 대뿐이라 죽으면 시세 수집이 멈춘다.
- 2대를 띄우면 둘 다 거래소에 직접 연결해 같은 코인을 구독하므로, 같은 체결이 Kafka에 2번씩 적재됐다
  (`BINANCE-BTCUSDT-6914105886`, offset 2278914·2278915, receivedAt 1.3ms 차이).

## 선택지
| 방법 | 장애 시 공백 | Kafka 데이터량 | 소비자 부담 | 비고 |
| --- | --- | --- | --- | --- |
| A1. 코인 나눠 맡기 | 재배정 전까지 해당 코인 중단 | 1배 | 없음 | 재배정 조율이 복잡, 처리량 확장에 유리 |
| A2. 리더 한 대만 수집 | 수 초~십수 초 | 1배 | 없음 | 리더 교대 처리 필요 |
| B. 둘 다 수집, 소비자가 eventId로 중복 제거 | 0 | 대수만큼 | 모든 소비자(캔들 등)가 중복 제거 | 금융권 이중화 피드 방식 |

## 결정
A2. Valkey 열쇠를 잡은 리더 한 대만 거래소에 연결하고, 나머지는 대기하다 리더가 죽으면 넘겨받는다.
collector의 수집(시세·환율)은 모두 리더만 한다.

## 이유
- **중복은 만드는 쪽에서 막는 게, 받는 쪽마다 막는 것보다 싸다.** 소비자는 앞으로 계속 늘어나므로(캔들, 알림, 통계, 배치) "Kafka엔 한 번만 들어온다"를 보장하면 뒤쪽이 단순해진다.
- 리더 교대 공백은 구간을 기록하고 공백 보정에서 거래소 REST로 채운다 (ADR 0020과 같은 원칙).
- B는 공백 0이 필요해지면 다시 검토한다. A2에서 B로 가는 것은 리더 선출을 끄고 중복 제거 단계를 더하는 것이라 길이 막히지 않는다.
- A1은 한 대가 모든 코인을 감당하지 못할 때 필요하다 (3단계 거래소 추가 시 검토).

## 동작
- 획득: 5초마다 `SET leader:collector {인스턴스 ID} NX PX 15000`. 성공하면 WebSocket `activate()`.
- 연장: 리더는 5초마다 Lua로 "열쇠가 내 것일 때만" 기한을 15초로 늘리고 살아 있던 시각(`leader:collector:renewed-at`)을 기록한다.
- 연장 실패(다른 인스턴스가 이미 가져감): 즉시 `deactivate()`. 리더가 둘이 되는 것(스플릿 브레인)을 막는다.
- Valkey 장애: 열쇠 상태를 확인할 수 없으므로 마지막으로 확인한 기한까지만 리더를 유지하고, 지나면 스스로 내려온다. 그 기한 전에는 다른 인스턴스도 열쇠를 가져갈 수 없다.
- 정상 종료: 시각을 기록하고 열쇠를 반납해 대기조가 기한을 기다리지 않고 넘겨받는다.
- 공백 기록: 새 리더는 획득 즉시 `renewed-at`부터 지금까지를 "리더 교대 공백"으로 로그에 남긴다. 옛 리더는 마지막 기록 후에도 최대 5초 더 수집했을 수 있어 실제보다 넓게 잡힌다 (놓치는 것보다 안전).
- WebSocket 클라이언트는 켤 때마다 세대 번호를 올려, 중단 전에 예약된 재연결이나 진행 중이던 연결이 중단 후 뒤늦게 실행되면 무시하거나 즉시 끊는다.
- 시작·종료 순서: 발행기(`BufferedTickerPublisher`)가 리더 선출보다 먼저 켜지고 나중에 꺼진다.

## 설정 근거
| 설정 | 값 | 근거 |
| --- | --- | --- |
| 열쇠 기한 | 15초 | 연장을 두 번 놓쳐도 유지되어 GC 등 잠깐의 멈칫으로 리더가 바뀌지 않음 |
| 연장 주기 | 5초 | 기한 안에 세 번 시도 |

## 구현 방식
Spring Integration(`RedisLockRegistry` + `LockRegistryLeaderInitiator`)도 검토했으나, `SET NX` + Lua 연장으로 동작이 명확하고 공백 기록 같은 동작을 넣기 쉬워 직접 구현했다.
`LeaderElection`은 `Runnable` 두 개(획득·해제)만 받아 WebSocket을 몰라도 되게 했고, 덕분에 Testcontainers 테스트에서 호출 횟수만 세는 가짜로 검증했다.

## 검증
- `LeaderElectionTest`: 한 대만 리더, 장애 시 기한 후 인계, 열쇠를 뺏기면 즉시 중단, 정상 종료 시 즉시 인계, 공백 기록, 최초 기동 시 공백 없음
- 2대 실행: 중복 적재 2번 → 1번, 정상 종료 인계 즉시(연결 약 0.2초), `kill -9` 인계 약 13.8초, 공백 로그 16,601ms (성능 002)

## 트레이드오프
- 장애 시 약 15~20초 실시간 공백 → 기록 후 공백 보정에서 채움
- 기록된 공백의 끝은 열쇠 획득 시각이라 실제 연결 완료(약 0.4초 뒤)보다 이르다 → 보정 시 구간 끝에 여유를 둔다.
- 정상 종료 공백(대기조의 다음 시도까지 최대 5초)은 "먼저 연결하고 나서 끊기"로 줄일 수 있다 → 6단계 무중단 배포에서 검토.
- 인스턴스 간 시계 차이는 공백 구간에 그대로 반영된다.
- 새 리더는 다음 환율 주기(최대 30분)까지 환율을 수집하지 않는다. 환율은 Valkey에 남아 있어 김프 계산에는 영향이 없다.
