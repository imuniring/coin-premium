# 0014. 김프 추이 API (김프 캔들)

- 상태: 채택
- 날짜: 2026-11-11

## 맥락
1분 스냅샷이 쌓였고, 이를 차트로 보여줄 조회 API가 필요하다. 구간을 묶을 때 평균만 주면 구간 내 변동이 보이지 않는다.

## 결정
- `GET /v1/coins/{symbol}/premium/history?from=&to=&interval=`
- interval: `1m`, `1h`, `1d` (기본 `1h`), from·to 생략 시 최근 1일, 범위는 `[from, to)`
- 구간마다 시가·고가·저가·종가·평균·개수(count)를 반환하는 **김프 캔들**
- `1d`는 KST 자정 기준으로 자르고, 응답 시각은 UTC
- 간격별 최대 기간: 1m 1일, 1h 31일, 1d 366일 (초과 시 400 `INVALID_RANGE`)
- 집계는 DB에서 수행 (jOOQ)
  - 시가·종가: `FIRST_VALUE ... OVER (PARTITION BY 구간 ORDER BY captured_at ASC/DESC)`
  - 구간 내림: 기준점(anchor)부터의 차이로 `TIMESTAMPADD(unit, TIMESTAMPDIFF(unit, anchor, t), anchor)`
  - 일 단위 기준점을 UTC 15:00(= KST 자정)으로 두어 시간대 변환 없이 KST 날짜 경계 집계

## 이유
- 캔들은 구간 내 김프의 출렁임(고가·저가)을 보여주고 차트에 바로 쓸 수 있다
- `count`로 구간 내 스냅샷 수를 노출해 데이터 공백을 클라이언트가 확인 가능 (1h 정상 60)
- 김프는 한국 사용자 지표라 하루 경계를 KST 자정으로 맞춤
- `[from, to)`로 기간을 이어 조회해도 같은 데이터가 중복 집계되지 않음
- 앱에서 집계하면 1d·1년 요청 시 50만 행 이상을 읽어야 해서 DB 집계 선택
- 최대 기간 제한으로 과도한 조회에 의한 DB 부하 방지
- 도메인의 `HistoryInterval`은 규칙(코드, 최대 기간)만 갖고, SQL 구간 계산은 jOOQ 어댑터가 담당

## 대안
- 평균만 제공: 단순하지만 구간 내 급변이 묻힘
- 앱 메모리 집계: 쿼리는 단순하지만 대량 조회 시 메모리·네트워크 부담

## 트레이드오프
- 1분 스냅샷 기반이라 1분 사이의 순간 변동은 고가·저가에 반영되지 않음 → "1분 해상도 지표"로 정의
- SQL 템플릿(`field(...)`) 사용으로 일부 타입 안전성 포기. 템플릿에는 상수만 넣고 사용자 입력은 바인딩되는 조건절에만 사용
- 데이터가 많아지면 사전 집계 테이블(1h·1d) 또는 파티셔닝 검토
