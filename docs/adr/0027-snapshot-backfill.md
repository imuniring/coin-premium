# 0027. 김프 스냅샷 공백 감지·보정

- 상태: 채택
- 날짜: 2026-11-27
- 관련: #77, #79, #83, #85, #87, ADR 0023, ADR 0025, ADR 0026, ADR 0028, 성능 003

## 맥락
- 시간순으로 쌓이는 데이터는 1분 김프 스냅샷(`premium_snapshot`)뿐이다. 체결은 저장하지 않는다 (체결·캔들 보정은 3단계).
- 스냅샷 공백 원인: premium 중단·배포, 스냅샷 실행 실패(ADR 0023의 한계), 데이터 준비 전, 시세가 오래돼 저장을 건너뜀(ADR 0026).
- collector의 짧은 끊김은 공백이 아니라 "오래된 시세"를 만든다. ADR 0026으로 이 경우도 공백이 되게 했다.

## 결정
최근 구간의 빈 분을 찾아, 거래소 과거 1분 캔들과 환율 이력으로 김프를 다시 계산해 `BACKFILL`로 저장한다. 10분마다 자동 실행한다.

## 출처 구분 (#77)
- V2: `source VARCHAR(10) NOT NULL DEFAULT 'LIVE'` + `CHECK (source IN ('LIVE','BACKFILL'))`. 기존 줄은 LIVE.
- ENUM 대신 VARCHAR + CHECK: 값 추가가 쉽고 DB 간 이식성이 높다.
- 저장 포트는 출처를 반드시 받는다. 기본값을 두면 보정 줄이 LIVE로 저장되는 실수를 막을 수 없다.
- 같은 `(symbol, captured_at)`에 LIVE가 있으면 BACKFILL은 무시된다 (`onDuplicateKeyIgnore`, 실시간 값 우선).

## 공백 감지 (#79)
- 있어야 할 분 − 저장된 분 = 공백, 연속된 빈 분은 구간(`GapRange`, 양 끝 포함)으로 묶는다.
- 검사 범위: 최근 6시간(`lookback`). 오래된 공백은 4단계 일일 배치가 넓게 점검한다.
- 최근 2분 제외(`settle-delay`): 실시간 저장이 끝나지 않은 분과 경쟁하지 않게 하고, 진행 중인 현재 분 캔들을 쓰지 않게 한다.
- 비교는 Java(`GapFinder`, 순수 계산)에서 한다. 코인당 최대 360줄이라 가볍고 DB 없이 테스트할 수 있다.
- 저장 포트와 조회 포트(`SnapshotTimeline`)를 나눠 저장 포트를 쓰는 테스트의 람다를 유지한다.

## 재료 (#83)
- `HistoricalPrices` 포트가 거래소별 응답을 "분 시작 시각 + 종가"(`MinuteClose`)로 통일한다.

| | Upbit | Binance |
| --- | --- | --- |
| API | `/v1/candles/minutes/1` | `/api/v3/klines?interval=1m` (시세 전용 `data-api.binance.vision`) |
| 캔들 시각 | 분 시작 (`candle_date_time_utc`, 시간대 표기 없음) | 분 시작 (open time) |
| 종가 | `trade_price` (숫자 → BigDecimal로 읽음) | 배열 5번째 (문자열) |
| 최대 개수 | 200, `to` 미포함, 최신순 | 1000, `endTime` 포함 → 1ms 차감 |
| 체결 없는 분 | 캔들 없음 | 캔들 없음 |

- 환율은 ADR 0028의 이력과 일자 전환 규칙을 쓴다.

## 보정 규칙 (#85)
| 항목 | 규칙 | 이유 |
| --- | --- | --- |
| 가격 | 분 m = 시작 시각 **m-1분** 캔들의 종가 | 실시간 스냅샷은 "m 직전 최신 체결". 시작 시각 m 캔들은 m 이후 가격이라 1분씩 밀린다 |
| 캔들 없음 | m-1분 캔들이 없으면 채우지 않음 | 더 앞 캔들의 체결은 반드시 60초를 넘어 ADR 0026과 어긋난다. 그 분은 실제로 값이 없다 |
| 계산 | `KimchiPremium.calculate` | 실시간과 공식 공유 |
| 체결 시각 | `traded_at` = 캔들 시작 시각 | 캔들로는 정확한 마지막 체결 시각을 알 수 없다 (`source`로 구분) |
| 결과 | 채움 / 못 채움(데이터 없음) / 실패(거래소 장애, 다음 실행 재시도) | 알림·리포트에서 성격이 다른 두 실패를 구분 |

## 실행 (#87)
- cron `30 */10 * * * *` + ShedLock(`premium-backfill`, lockAtMostFor 9m, lockAtLeastFor 1m)
- `fixedDelay`는 인스턴스마다 실행 시각이 어긋나 짧은 락으로 중복을 막을 수 없어 cron으로 시각을 맞춘다 (collector 환율과 같은 이유).
- 매분 0초 스냅샷과 겹치지 않게 30초에 실행한다.
- 같은 구간을 다시 실행해도 UNIQUE로 결과가 같다 (멱등).
- 수동 실행(오래된 공백, 특정 구간 재보정)은 4단계 Spring Batch에서 범위를 받아 같은 로직을 부른다.

## 트레이드오프
- 체결이 없던 분은 영구히 비어 있다 (6시간 뒤 검사 범위에서 빠진다).
- 거래가 뜸한 코인은 공백이 많고 보정도 어렵다 (ADR 0026 다시 볼 조건과 같다).
- Upbit 시세 API 호출 제한은 공식 문서로 재확인이 필요하다.
