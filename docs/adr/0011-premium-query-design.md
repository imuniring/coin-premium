# 0011. premium-service 조회 설계 (메모리 최신값 + 요청 시 계산)

- 상태: 채택
- 날짜: 2026-11-11

## 맥락
김프를 계산하려면 코인별 국내 최신가, 해외 최신가, 최신 환율이 필요하다. 시세는 초당 수십 건씩 들어오고, 조회 API는 여러 스레드에서 동시에 읽는다.

## 결정
- 최신 시세·환율만 메모리에 보관하고, 조회 요청 시 그 자리에서 김프를 계산한다
  - 시세: `ConcurrentHashMap` (key = `거래소:심볼`), `merge`로 체결 시각이 더 최신일 때만 교체
  - 환율: `AtomicReference`, `accumulateAndGet`으로 더 최신일 때만 교체
- 저장소는 포트(`MarketDataRepository`)로 분리해 2단계에서 Redis로 교체 가능하게 한다
- 기동 시 Kafka 읽기 위치: 환율 토픽은 처음부터, 시세 토픽은 끝부터 (`ConsumerSeekAware`)
- 메시지는 문자열로 받아 직접 역직렬화하고, 실패 메시지는 로그 후 건너뛴다
- 응답 규칙
  - 지원하지 않는 코인: 404 (기다려도 생기지 않음)
  - 시세·환율 준비 전: 503 + `Retry-After` + 누락 목록(`missing`)
  - 파라미터 누락·공백: 400
  - 에러 형식은 ProblemDetail로 통일
- 응답에 계산에 쓴 원본 값과 시각(`tradedAt`, `publishedAt`)을 포함한다

## 이유
- `get → 비교 → put` 조합은 사이에 다른 스레드가 끼어들 수 있어 원자적 연산 사용
- 재연결 등으로 순서가 뒤바뀐 과거 시세가 최신값을 덮지 않도록 체결 시각 비교
- 환율은 하루 1회만 오고 collector는 같은 환율을 다시 보내지 않으므로, 재시작 시 토픽 처음부터 읽어 복구
- 데이터가 없을 때 0%를 반환하면 실제 값으로 오해할 수 있음 → 명시적 에러
- 서비스는 상황(예외)만 알리고 HTTP 상태 코드는 웹 어댑터가 결정 → 조회 방식이 바뀌어도 서비스 재사용

## 트레이드오프
- 메모리 저장소는 인스턴스마다 따로라 다중 인스턴스에서 값이 다를 수 있음 → 2단계 Redis
- 원본 값의 신선도(오래된 시세) 판단은 아직 클라이언트에 맡김 → 5단계 신선도 모니터링
