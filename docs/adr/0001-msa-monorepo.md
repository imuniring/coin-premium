# 0001. MSA + 모노레포 구성

- 상태: 채택
- 날짜: 2026-11-05

## 맥락
수집(외부 거래소 의존, 쓰기 부하)과 조회(읽기 부하)는 장애 원인과 트래픽 패턴이 다르다. 거래소가 느려지거나 죽어도 조회 API는 살아 있어야 하고, 거래소를 추가할 때 수집 쪽만 배포하고 싶다.

## 선택지
- A: 모놀리스
- B: 모듈러 모놀리스 (하나의 앱, 모듈 경계 분리)
- C: MSA (서비스 분리 + Kafka 비동기 통신)

## 결정
C. MSA로 구성하되 저장소는 하나(모노레포, Gradle 멀티 모듈)로 관리한다. 1단계는 collector, premium 두 서비스와 공통 모듈 event-contract로 시작한다.

## 이유
- 장애 격리: 수집 장애가 조회에 전파되지 않음
- 독립 확장: 수집·조회를 각각 스케일링
- 독립 배포: 거래소 추가 시 collector만 배포
- 모노레포로 이벤트 계약 변경을 한 PR에서 producer·consumer 함께 반영 가능

## 트레이드오프
- 혼자 운영하기엔 인프라·배포 복잡도가 높다 → 서비스는 작게 시작해 필요할 때 추가
- K8s 환경을 전제로 Eureka·Config Server 대신 K8s Service·ConfigMap 사용 예정
- 서비스 간 트랜잭션이 없도록 "수집 → 이벤트 → 처리" 흐름으로 설계 (Saga 불필요)
